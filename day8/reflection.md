# Course Reflection

The most difficult concept in the course was handling high-concurrency race conditions and understanding database transaction isolation levels. Early on, ensuring data consistency seemed trivial using standard SQL transactions. However, realizing how subtle race conditions cause duplicate seat bookings when thousands of requests hit the same record simultaneously exposed the real limits of naive relational database locking[cite: 1, 2]. I overcame this challenge by systematically breaking down isolation levels, building small test cases to recreate deadlock conditions, and learning how optimistic locking patterns and distributed memory caches like Redis can absorb heavy write contention before it reaches the disk[cite: 1].

Based on the feedback received on my capstone project, I would improve the system's observability and automated error recovery pipelines[cite: 1]. While the application logic worked well during standard workflows, the architecture lacked detailed distributed tracing across asynchronous tasks. When edge-case network latency occurred between background worker jobs and third-party payment callbacks, diagnosing root causes required tedious manual inspection. I plan to incorporate structured logging, clear OpenTelemetry spans, and automated dead-letter queues to catch and retry failed transactions gracefully.

Next, I will deepen my knowledge of distributed systems and scalable backend infrastructure[cite: 1]. Specifically, I want to master event-driven streaming with Apache Kafka, study microservices orchestration using Docker and Kubernetes, and explore cloud-native deployment patterns on major cloud platforms to design fault-tolerant, horizontally scalable applications.
